    Step 1

    Pick hardware that makes steering testable early.

    The first build uses a Seeed XIAO ESP32-C3, two small ERM vibration motors, MOSFET low-side switches, and a light 1S LiPo. The design keeps the electronics small enough for a skittering chassis while still leaving enough PWM channels, Wi-Fi, and flash for browser control.

    Design decision: Wi-Fi AP control beats BLE for the MVP because any phone can open a local page without pairing or installing an app.

    Core stack

    Small Wi-Fi controller, enough PWM pins, and a compact 21 x 17.8 mm footprint.

    Step 2

    Switch motor current outside the microcontroller.

    Each motor is driven through an N-MOSFET. The ESP32-C3 pin only drives the MOSFET gate; motor current flows from the battery through the motor and MOSFET to ground.

    Design decision: MOSFETs are lighter than a full dual H-bridge and are enough because vibration motors only need one direction.

    Repeat this low-side switch once for the left motor and once for the right motor.

    Step 3

    Centralize every hardware assumption.

    Pin assignments and safety constants live in one firmware file so the robot can be rewired without hunting through the codebase. The placeholder pins are D2 and D3 for motor PWM.

    Design decision: Hardware mappings are isolated in config.h because pin labels may vary between board packages and must be checked before soldering. 
    LEFT_MOTOR_PWM_PIN  = D2
RIGHT_MOTOR_PWM_PIN = D3
COMMAND_TIMEOUT_MS  = 500
MAX_DUTY            = 0.80
RAMP_RATE           = 2.0 / second

    Step 4

    Wrap motor output in a safety layer.

    Browser input never writes PWM directly. The MotorDriver clamps values, applies max duty, ramps changes, adds a short start boost, and cuts output immediately when commands go stale.

    Design decision: Timeout is hard-stop, not ramp-down, so closing the page or losing Wi-Fi stops the robot within the configured safety window.

    Motor safety flow

    1. Receive JSON command
    2. Clamp and trim target
    3. Ramp toward target
    4. Apply PWM through LEDC
    5. Stop instantly after 500 ms stale input

    Step 5

    Convert joystick movement into left and right motor intensity.

    The mixer accepts throttle from 0 to 1 and turn from -1 to 1. Negative turn makes the right motor stronger for a left curve; positive turn makes the left motor stronger for a right curve.

    Design decision: The mixer normalizes both sides so aggressive turning never exceeds the safe duty range.

    Step 6
    
            
    Serve the controller from the robot itself.
    
            
    
              The ESP32-C3 starts an access point named VibroBug-XXXX and serves a joystick UI
              at 192.168.4.1. The page sends commands every 75 ms while the user is touching
              the joystick and posts /stop on release.
            
    
            
    
              Design decision:
              The control page lives in firmware, so the robot can be driven from a phone without internet,
              Bluetooth pairing, or a laptop.

    Step 7
    
            
    Expose small JSON endpoints for testing and tuning.
    
            
    
              The API supports mixed drive commands, direct motor tuning, pattern playback, status reads,
              config updates, and immediate stop. This makes bench testing possible before the phone UI is used.
            
    
            
    
              Design decision:
              Direct mode is kept alongside joystick mode because vibration locomotion depends on mechanics
              and needs repeatable left/right experiments.
            
    
          
    
          
    
            
    
              
              
              
              
            
    
            
    
          
    
        
    

        
    
          
    
            
    Step 8
    
            
    Tune the body before blaming the firmware.
    
            
    
              The firmware can steer only if the mechanics convert vibration into directional slip.
              Test bristle angle, motor placement, motor orientation, battery position, surface, and body mass.
            
    
            
    
              Design decision:
              The build protocol starts ugly because the first success criterion is repeatable skittering,
              not a polished shell.

    Step 9
    
            
    Treat the first robot as a lab prototype.
    
            
    
              The early build has exposed electronics, bristles, solder joints, wires, and a LiPo. It is useful
              for engineering tests but not safe for animal play until enclosed and durability-tested.
            
    
            
    
              Design decision:
              Firmware limits are necessary, but physical enclosure, strain relief, part retention, and a power
              switch are what make the later cat-toy version credible.
